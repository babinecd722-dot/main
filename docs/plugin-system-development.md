# Сборка и проверка системного API плагинов

Слой Telegram API закреплён переменной `TELEGRAM_IOS_COMMIT` в
`.github/workflows/build-aorusgram.yml`. Мост плагинов генерируется из исходников этого
слоя, поэтому имена, типы, флаги и TL ID соответствуют собираемому клиенту.
`AorusPluginTL.generated.swift` создаётся при сборке и не хранится в репозитории.

## Генерация

```sh
python3 scripts/gen_plugin_tl.py \
    /path/to/Telegram-iOS/submodules/TelegramApi/Sources \
    /path/to/Telegram-iOS/submodules/TelegramApi/Sources/AorusPluginTL.generated.swift
```

В тот же каталог копируется `patches/submodules/TelegramApi/Sources/AorusPluginTL.swift`.
Оба файла компилируются в TelegramApi. Генератор вызывает штатные функции и конструкторы;
собственного сериализатора плагинов нет. Проверка двоичных границ использует описания
этого же слоя до вызова штатного парсера.

Генератор сверяет методы с FunctionDescription, а конструкторы — с таблицей парсеров
Telegram. Неизвестная форма объявления или неполный каталог прерывают сборку.
При изменении структуры исходников Telegram следует обновить генератор.

## Строки интерфейса

Названия и описания разрешений в `AorusPluginControllers.swift` используют
`aorusL(ru, en)`. Русский и английский тексты задаются в месте вызова, остальные
языки — в `AorusL10nTable.swift`. Ключ каждой записи совпадает с английским текстом
целиком. При удалении строки удаляется её ключ; форматные подстановки сохраняются
в переводе.

```sh
python3 scripts/aorus_l10n_check.py .
python3 scripts/tests/test_aorus_l10n_check.py
```

Проверка читает строки экранов и патчей Telegram, сверяет ключи, повторения и
подстановки. Она выполняется до загрузки Telegram и повторно в проверке оформления
собранного дерева исходников.

## JavaScript

```sh
python3 scripts/plugin_prelude_check.py .
python3 scripts/plugin_system_prelude_check.py .
```

Первая проверка выполняет прелюдию и проверяет разрешения, события и существующий API.
Вторая проверяет MTProto, описание и пагинацию, ошибки RPC, отмену, последовательные
пакеты, сетевой профиль, двоичные HTTP-данные и все методы Files API. Host отвечает через тот же dispatcher,
который использует клиент; настоящий аккаунт не задействуется.

## TL и нативный транспорт

```sh
python3 scripts/plugin_tl_check.py . \
    /path/to/Telegram-iOS/submodules/TelegramApi/Sources \
    --export-api /tmp/aorus-plugin-api
python3 scripts/plugin_system_native_check.py . /tmp/aorus-plugin-api \
    --telegram-core-sources /path/to/Telegram-iOS/submodules/TelegramCore/Sources
```

Нужны Python 3, Node и Swift. Путь к Swift задаётся через `--swiftc`.
TL-проверка компилирует настоящий TelegramApi с мостом. Каждый конструктор проходит
проверку ID, кодирования, разбора и повторного кодирования; каждый RPC — подготовку
запроса и парсер результата. Необязательные поля проверяются по группам флагов.
Также проверяются неверные типы, большие целые, обрезанные ответы, лишние байты и векторы.

Нативная проверка использует собранный TelegramApi и управляемый транспорт вместо
соединения с Telegram. Проверяются аккаунт, передача Updates менеджеру состояния,
ошибки, deadline, отмена, повторное использование ID и лимит запросов.
Мост передачи Updates компилируется внутри TelegramCore; сигнатура и доступ
метода в тестовом заменителе сверяются с исходником закреплённой версии Telegram.
HTTP проверяется на локальном сервере: байты, потоковый лимит, перенаправления,
заголовки, отмена и файлы. Файловый API компилируется из исходника клиента;
проверяются создание, перезапись, квота, параллельное добавление, папки, Unicode-пути,
копирование, перемещение и двоичные порции. ZIP проверяется в обе стороны со стандартным
архиватором Python: сохранённые и Deflate-записи, пустые папки, контрольные суммы,
обрезанные данные и откат ошибочной распаковки.

На Linux адаптируется только тестовая копия Buffer.swift: Foundation иначе объявляет
NSMutableString и C-указатели. Исходники Telegram не изменяются.
Для WebSocket используются completion-формы Apple API или тестовый адаптер к
async-формам swift-corelibs.

Проверки не отправляют RPC на сервер Telegram. Сериализация не подтверждает серверные
права аккаунта, доступность метода или выполнение платежа.
Полная сборка iOS и проверки UIKit выполняются существующим workflow на macOS.

## Экспорт и иконки

```sh
python3 scripts/plugin_exports_check.py .
python3 scripts/plugin_icons_check.py . --telegram-source /path/to/Telegram-iOS
python3 scripts/plugin_ai_check.py .
python3 scripts/plugin_screens_check.py .
python3 scripts/tests/test_swift_call_label_check.py
```

Каталог экранов и ссылки проверяет `plugin_screens_check.py`: каждый маршрут проходит
через настоящий резолвер, модель вкладки, строку страницы и ярлык настроек. Проверяются
формат ссылки, несовместимые назначения, кодирование вкладок и рекомендации разрешений.
Нативные методы открытия извлекаются из runtime без изменений и выполняются с управляемыми
фабрикой и навигацией: все стили, текущий аккаунт и плагин, отказ фабрики, отсутствие
навигации и выполнение после повторной проверки доступа. JavaScriptCore в workflow
проверяет вызовы API и продолжение работы после неизвестного маршрута.

После упаковки `ipa_check.py` проверяет CRC всего архива, единственный основной пакет,
идентификатор приложения, номер текущей сборки и исполняемый файл Mach-O arm64.
В журнал сборки выводятся размер и SHA-256 файла IPA.

Экспорт справочника использует тот же текст, который показывается в клиенте.
Проверка компилирует настоящий форматтер и проверяет обе языковые версии,
Markdown-примеры, время UTC, уровни и многострочные записи консоли.

Пиксельная проверка компилирует функции отрисовки из Display. Набор изображений
проверяет связность контуров, отверстия, отдельные точки, цвета и градиенты, прозрачность,
размер холста и повторяемость результата. На macOS обработчик иконок также
проверяется с iOS SDK и запускается в доступном iPhone-симуляторе: три загрузчика
SF Symbols, растеризация, размер, повторное применение стиля, замена голосового
ввода, превью и сброс стиля. Проверяются также цвет UIImageView в светлом и тёмном
оформлении, масштаб Retina, символы SwiftUI-панели форматирования и её моноширинная
кнопка. Проверяется также рисуемый значок: ориентация, цвет и прозрачность, ограничение
размера, область действия и восстановление оригинала. Для этой части нужен установленный iOS Simulator.
Для значков из слоёв проверяются диапазон штриха, цвет, прозрачность, сохранение исходных
контуров и повторная отрисовка после скрытия нативных слоёв.
Из подготовленного дерева извлекаются настоящие функции обеих стрелок возврата,
кэш обычной стрелки и подписка кнопки диктовки на смену стиля. Проверяются
изменение отображаемой формы, обновление открытого чата, сила пикселя, цвет темы,
область действия, сброс стиля и освобождение панели вместе с её подпиской.
Проверка нативной темы использует обработчик стиля общего контроллера Display.
При светлом и тёмном режиме устройства формы получают стиль темы приложения,
а системный режим окна остаётся прежним.
Стиль проверяется также у корневого view, загруженного после выбора темы,
без принудительной ранней загрузки интерфейса. Кнопки экспорта, очистки и оформления
проверяются по выражениям из исходников клиентских контроллеров: шаблонная отрисовка,
белый и красный цвет панели, обычная и пиксельная форма.
Общий символ SwiftUI проходит проверку с iOS SDK вместе с обработчиком UIKit. Проверяется
крупный системный символ, а проверка дерева исходников отклоняет прямые загрузчики
Image(systemName:) и Label(systemImage:) в модулях AorusGram и AorusGramUI.
Заменитель AppBundle передаёт только загрузку ресурсов; UIKit и Objective-C runtime
используются настоящие.

Проверка AI компилирует класс хода и методы клиентского хоста из исходников runtime.
Управляемый транспорт позволяет проверить подтверждение серверного хода перед
следующим запросом, повторные обращения, отмену, ошибки сети, квоту и смену аккаунта.
Проверяются продолжения после инструмента и разрешения, ранний ответ плагина,
повторный ответ, ограничение числа потоков и запоздавшие события старого хода.
JavaScript-проверка запускает настоящий prelude, передаёт историю между вопросами
и проверяет очистку беседы во время запроса и восстановление после ошибки.

JavaScriptCore-проверка в workflow создаёт файл плагина, читает его метаданные,
импортирует его в отдельное хранилище и проверяет выключенное состояние.
Отправка документов использует штатную очередь Telegram. Проверки без аккаунта
подтверждают формирование запросов и разрешения, но не доставку документа на сервер.

## Запуск и возврат из фона

```sh
python3 scripts/client_lifecycle_check.py .
```

Проверка применяет настоящие функции настройки стартового экрана к исходному
и ранее настроенному XIB, проверяет чёрный фон и повторное применение настройки.
Поверхность окна остаётся чёрной до получения темы аккаунта.

Конвейер загрузки проверяется на настоящих методах менеджера с файловым хранилищем
и интерфейсом в роли заменителей. Чтение файлов, хеширование исходников и анализ
разрешений выполняются на отдельной последовательной очереди. Применение снимка
происходит на главном потоке после проверки поколения хранилища и последнего запроса.
Проверка охватывает запуск, повторный вход, смену исходника во время чтения, удаление,
недоступность защищённых данных и отказавший при запуске плагин.

Методы HUD проверяются на объединение одновременно запрошенных замеров и отказ
от результата для уже закрытого окна. На macOS обе реализации замера CPU проходят
1200 последовательных вызовов: число прав на Mach-порт текущего потока должно
остаться прежним. Счётчики ядра, сети и диска собираются в фоне; состояние UIKit
читается и отображается на главном потоке.

Эти проверки подтверждают конкретные причины задержек и утечек. Сценарий возврата
после 20 минут в другом приложении требует отдельной проверки на устройстве.

Локальные данные профиля проверяет `scripts/local_profile_check.py`. Он компилирует
исходные функции номера, общего переключения Pixel, рейтинга и конвертации подарка
с заменителями Postbox и Keychain. Проверяются форматы и сохранение номера, суммы покупки
в нанотонах и центах USD, их смена вместе с номером, восстановление повреждённых
метаданных и сохранение цены при повторном открытии карточки. Также проверяются восстановление
обычного номера, проценты рейтинга, границы уровней, отрицательные значения, перенос
истории, изоляция аккаунтов и одновременные покупки и конвертации. Проверка использует
настоящие функции чтения, списания и пополнения баланса; значения Int64 сохраняются
без промежуточного преобразования в Double. Связь с нативным профилем, карточкой номера
и обоими путями Pixel проверяется после наложения патчей на исходники Telegram.
Отдельно компилируется запись покупки вместе с настоящим хранилищем истории и журналом
рейтинга. Проверяются первое улучшение после переноса истории, перепродажа, подарок
Premium, одновременная запись покупок и восстановление баллов улучшений из истории.

### Детали сообщений и RGB

`python3 scripts/message_details_check.py . --telegram-source telegram-ios` компилирует
каталог оформления, геометрию баблов и нативные форматтеры статуса. Данные пользователей и
строки локализации задаются фикстурами. Проверяются оба направления, сохранение углов и
стыков при скрытии хвостика, независимое время сообщения, точные и приблизительные статусы,
часовые пояса, переходы дат и форматы 12/24 часа.

`plugin_icons_check.py` на macOS запускает UIKit в симуляторе. Проверка растровых баблов
использует нативный код заливки, маски и обводки на буфере CoreGraphics; сравниваются размеры,
точки растяжения и пиксели до скрытия хвостика, после него и после возврата. RGB проверяется
на настоящих цветах UIKit, слоях Core Animation и строках CoreText: прозрачность, замкнутый
цикл, неподвижные цвета рядом с RGB, маски галочек, приостановка в фоне, возобновление и
удаление владельца. В рабочем клиенте RGB не вызывает обновлений темы или вёрстки на кадрах.
